  <name>Task 3: Investigate and document expires format difference between Go and NestJS</name>
  <files>server/test/api-compat/auth-api-compat.spec.ts</files>
  <behavior>
    - Test: Login response expires field type assertion -- verify whether NestJS returns string or number
    - Test: Token refresh response expires field type assertion -- verify whether NestJS returns string or number

  <action>
Investigate the expires format difference identified in RESEARCH.md Section 8 (HIGH Risk #1).

Go's token_service.go (line 73) returns `expiresAt int64` from `claims.ExpiresAt.Time.UnixMilli()`. When this int64 is placed in `gin.H{"expires": expiresAt}`, Go's JSON encoder serializes it as a JSON NUMBER (e.g., `1721376000000`).

NestJS's token.service.ts (line 92) returns `String(Date.now() + 15 * 60 * 1000)`, which serializes as a JSON STRING (e.g., `"1721376000000"`).

The frontend type definition has `expires: string`, suggesting the frontend expects a string. But if Go returns a number, the frontend must handle both types.

Add test assertions that explicitly check the type of expires:
1. In login success test: `expect(typeof data.expires).toBe('string')` -- if this passes, NestJS returns string
2. In token refresh test: `expect(typeof res.body.data.expires).toBe('string')` -- same check

If the test confirms NestJS returns a string, add a comment noting this differs from Go's number format. The fix decision (whether to change NestJS to return number or keep string) is deferred to the risk marking phase (Plan 04), which will flag this as a HIGH risk compatibility gap.

Also check: does the frontend's auth-storage (Zustand store) or TokenManager parse expires? Read frontend/src/lib/api/client.ts and frontend/src/types/auth.ts to understand how the frontend consumes the expires value. If the frontend does `parseInt(expires)` or `Number(expires)`, then both string and number formats would work. If it does `new Date(expires)`, that would fail for a number.

Document the finding as a comment block at the top of the auth test file under a "## Known Compatibility Gaps" heading.
