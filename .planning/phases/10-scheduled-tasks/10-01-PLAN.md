### Task 3: Add view count in-memory Map to ArticleService

**What:** Replace direct DB increment with in-memory Map for view counts, matching Go backend's Redis key pattern `anheyu:article:view_count:{publicId}`. This **upgrades D-65** (Phase 03 simple increment) to batched sync mode.

**Files:**
- `server/src/article/article.service.ts` — add viewCountMap, modify getPublic to increment Map instead of DB
- `server/src/article/article.module.ts` — export ArticleService for ScheduleModule access

**How:**

1. In `ArticleService`, add:
   ```typescript
   private viewCountMap = new Map<string, number>(); // key format: article:view_count:{publicId}
   ```
   Key format: `article:view_count:{publicId}` (matches Go Redis key `anheyu:article:view_count:{publicId}` minus prefix)

2. In `getPublic()` method, **replace** `this.articleRepo.incrementViewCount(article.id)` with:
   ```typescript
   const publicId = encodePublicID(article.id, EntityType.Article);
   const key = `article:view_count:${publicId}`;
   this.viewCountMap.set(key, (this.viewCountMap.get(key) ?? 0) + 1);
   ```
   This matches Go backend's `cacheSvc.IncrBy(ArticleViewCountKey(publicID), 1)` pattern.

3. Add public getter/clear methods:
   ```typescript
   getViewCountMap(): Map<string, number> { return this.viewCountMap; }
   clearViewCountKeys(keys: string[]): void { keys.forEach(k => this.viewCountMap.delete(k)); }
   ```

4. In `article.module.ts`, add `exports: [ArticleService]` so SyncViewCountsJob can access it.

**⚠️ Breaking change from D-65:** This replaces the per-request DB increment with in-memory batching. Map is volatile — counts lost on crash (matches Go backend Redis behavior). The tradeoff is acceptable for a personal blog.

**Verify:** Viewing an article increments the in-memory Map; DB view_count is NOT immediately updated.

### Task 5: Add StatisticsService aggregation methods

**What:** Add aggregateDaily, getLastStatDate, getFirstLogDate methods. **⚠️ Architecture note:** Current StatisticsRepository uses real-time upsert (D-167) on each visit. The aggregation job serves as a **verification/correction** mechanism — it recalculates stats from raw visitor_logs and corrects any discrepancies (e.g., from service downtime where logs were recorded but stats not upserted).

**Files:**
- `server/src/statistics/statistics.repository.ts` — add 3 repository methods
- `server/src/statistics/statistics.service.ts` — add 3 service methods
- `server/src/statistics/statistics.module.ts` — export StatisticsService

**How:**

1. In `StatisticsRepository`, add:

   - **`aggregateDaily(date: Date): Promise<void>`** — **Reconciliation mode (DELETE + re-INSERT)**:
     - Compute date range using existing `getChinaDayBounds(date)` helper
     - Delete existing visitor_stats row for this date: `DELETE FROM visitor_stats WHERE date = {date}`
     - Re-aggregate from visitor_logs:
       ```sql
       INSERT INTO visitor_stats (date, unique_visitors, total_views, page_views, bounce_count)
       SELECT
         {date},
         COUNT(DISTINCT visitor_id),
         COUNT(*),
         COUNT(DISTINCT url_path),
         SUM(CASE WHEN is_bounce = 1 THEN 1 ELSE 0 END)
       FROM visitor_logs
       WHERE created_at >= {startTs} AND created_at <= {endTs}
       ```
     - Use `this.db.run(sql`...`)` for raw SQL (Drizzle's `sql` template)
     - If no visitor_logs exist for the date, simply ensure no visitor_stats row exists (already deleted)
     - Use `this.db.transaction()` for atomicity (delete + insert in one transaction)

   - **`getLastStatDate(): Promise<Date | null>`**:
     - `SELECT MAX(date) FROM visitor_stats`
     - Return null if no rows

   - **`getFirstLogDate(): Promise<Date | null>`**:
     - `SELECT MIN(created_at) FROM visitor_logs`
     - Convert Unix timestamp result to Date
     - Return null if no rows

2. In `StatisticsService`, add thin wrappers that delegate to repository:
   - `async aggregateDaily(date: Date): Promise<void>` — calls `this.repo.aggregateDaily(date)`
   - `async getLastStatDate(): Promise<Date | null>` — calls `this.repo.getLastStatDate()`
   - `async getFirstLogDate(): Promise<Date | null>` — calls `this.repo.getFirstLogDate()`

3. In `statistics.module.ts`, add `exports: [StatisticsService]`.

**Why reconciliation mode instead of pure aggregation:** The existing `upsertVisitorStats()` (D-167) writes stats in real-time on each visit. A pure "aggregate from scratch" job would duplicate data if run alongside real-time upserts. The reconciliation approach (DELETE then re-INSERT from raw logs) ensures data accuracy regardless of the real-time upsert state, and naturally handles cases where the service was down and logs accumulated without stats updates.

**Verify:** `aggregateDaily` correctly recalculates visitor_stats from visitor_logs for a given date; getLastStatDate returns the most recent stat date; getFirstLogDate returns earliest log date.

### Task 6: Implement 7 cron jobs

**What:** Create all 7 cron job classes in `server/src/schedule/jobs/` directory, each using `@Cron()` decorator from @nestjs/schedule.

**Files:**
- `server/src/schedule/jobs/cleanup-abandoned-uploads.job.ts`
- `server/src/schedule/jobs/statistics-aggregation.job.ts`
- `server/src/schedule/jobs/sync-view-counts.job.ts`
- `server/src/schedule/jobs/link-health-check.job.ts`
- `server/src/schedule/jobs/scheduled-publish.job.ts`
- `server/src/schedule/jobs/article-history-cleanup.job.ts`
- `server/src/schedule/jobs/scheduled-backup.job.ts`
- `server/src/schedule/jobs/index.ts` — barrel export

**How:**

Each job follows the same pattern:
```typescript
@Injectable()
export class XxxJob {
  private readonly logger = new Logger(XxxJob.name);

  constructor(
    private readonly scheduleService: ScheduleService,
    // ... specific dependencies
  ) {}

  @Cron('0 3 * * *') // or appropriate schedule
  async handleCron() {
    await this.scheduleService.runJob(XxxJob.name, async () => {
      // job logic
    });
  }
}
```

**Job details:**

1. **CleanupAbandonedUploadsJob** (`0 3 * * *` — daily 3:00 AM):
   - Inject `UploadService`
   - Call `this.uploadService.cleanupAbandonedUploads()` (**new method** — see Task 7)
   - Log cleaned count

2. **StatisticsAggregationJob** (`0 1 * * *` — daily 1:00 AM):
   - Inject `StatisticsService`
   - Compute yesterday in China timezone (UTC+8): `new Date(Date.now() - 86400000)` adjusted for UTC+8
   - Use `getChinaYesterday()` helper from `common/utils/time.util.ts` (add if not exists)
   - Call `this.statisticsService.aggregateDaily(yesterday)`
   - 10-minute timeout via `Promise.race([aggregateDaily(), timeout(600000)])`

3. **SyncViewCountsJob** (`0 2 * * *` — daily 2:00 AM):
   - Inject `ArticleService`, `ArticleRepository`
   - Get view count Map: `const map = this.articleService.getViewCountMap()`
   - If empty, log and return
   - For each key `article:view_count:{publicId}`:
     - Trim prefix to get publicId
     - Decode via `decodePublicID(publicId)` → `{ dbID, entityType }`
     - **Validate** `entityType === EntityType.Article` (skip invalid keys)
     - Build `Map<number, number>` of dbId → increment
   - Call `this.articleRepo.batchUpdateViewCounts(updates)` — uses `UPDATE articles SET view_count = view_count + {increment} WHERE id = {dbId}` (increment, not absolute)
   - Clear processed keys: `this.articleService.clearViewCountKeys([...map.keys()])`
   - Log synced count
   - Matches Go: Scan keys → GetAndDeleteMany → decode public IDs → batch UpdateViewCounts

4. **LinkHealthCheckJob** (`0 3 * * *` — daily 3:00 AM):
   - Inject `LinkService`
   - Call `this.linkService.forceHealthCheck()` (new public method — see Task 7)
   - This reuses the existing `runHealthCheckAsync()` logic (10 concurrent, 10s timeout, 2xx/3xx healthy)
   - 10-minute overall timeout
   - Log results

5. **ScheduledPublishJob** (`* * * * *` — every minute):
   - Inject `ArticleRepository`, `RssService`, `MemoryCache` (or specific cache refs)
   - Call `this.articleRepo.findScheduledArticlesToPublish()`
   - For each article:
     - Call `this.articleRepo.publishArticle(article.id)`
     - **Invalidate article-level caches**: `article:html:{publicId}`, `article:html:{abbrlink}`
   - If any articles published:
     - **Invalidate global caches**: `rss:feed:latest`, `home:articles:cache`, `home:featured:cache`, `sidebar:recent:cache`
     - Call `this.rssService.invalidateCache()`
   - Log published count (success + fail separately)
   - Matches Go: FindScheduledArticlesToPublish → PublishScheduledArticle per article → invalidateArticleCache + invalidateGlobalCaches

6. **ArticleHistoryCleanupJob** (`30 3 * * *` — daily 3:30 AM):
   - Inject `ArticleHistoryService`
   - Call `this.articleHistoryService.cleanupOldVersions()` (new method — see Task 7)
   - Log cleaned count

7. **ScheduledBackupJob** (`0 4 * * *` — daily 4:00 AM):
   - Inject `BackupService` (from Plan 10-03, but stub for now)
   - Retry logic: up to 3 attempts with backoff (10s, 20s, 30s)
   - Call `this.backupService.createBackup('定时自动备份', true)`
   - 5-minute timeout
   - Log filename and size on success
   - **Stub:** If BackupService not yet available, log "BackupService not available" and return

**Register all jobs as providers in ScheduleModule.**

**Verify:** Each job's `@Cron` decorator is recognized by @nestjs/schedule; jobs log execution on schedule.

   - Neither cleans up **abandoned upload records in the database** (file_entity rows with upload_session_id set and created_at > 24h ago)
   - Implementation:
     ```typescript
     async cleanupAbandonedUploads(): Promise<number> {
       const cutoff = new Date(Date.now() - 24 * 60 * 60 * 1000);
       // Find file_entity records where upload_session_id IS NOT NULL AND created_at < cutoff
       const abandoned = await this.db.select()
         .from(fileEntities)
         .where(and(isNotNull(fileEntities.uploadSessionId), lt(fileEntities.createdAt, cutoff)));
       // Delete each abandoned file entity and its disk files
       for (const file of abandoned) {
         await this.fileSystemService.deleteFile(file.uri);
         await this.db.delete(fileEntities).where(eq(fileEntities.id, file.id));
       }
       return abandoned.length;
     }
     ```
   - Matches Go: `uploadSvc.CleanupAbandonedUploads(ctx)` which cleans up incomplete upload records

### Task 8: Implement startup catch-up for missed aggregation

**What:** On application startup, check for missed aggregation dates and backfill them, matching Go backend's `CheckAndRunMissedAggregation`.

**Files:**
- `server/src/schedule/schedule.service.ts` — add `onModuleInit` with catch-up logic
- `server/src/schedule/schedule.module.ts` — ensure ScheduleService is initialized on startup

**How:**

1. In `ScheduleService`, implement `OnModuleInit`:
   ```typescript
   async onModuleInit() {
     // Fire-and-forget: don't block app startup
     this.dispatch('CheckAndRunMissedAggregation', async () => {
       await this.runMissedAggregationCatchUp();
     });
   }
   ```

2. `runMissedAggregationCatchUp()`:
   - Get last stat date: `this.statisticsService.getLastStatDate()`
   - If null (never aggregated): get first log date: `this.statisticsService.getFirstLogDate()`
   - If still null (no logs at all): return
   - Compute date range: from `startDate` (day after last stat, or first log date) to `yesterday` (China timezone)
   - Iterate day-by-day, calling `this.statisticsService.aggregateDaily(date)` for each
   - Stop on first error (don't continue to next day)
   - 30-minute timeout for the entire catch-up process (via `Promise.race`)
   - Log progress: "追补聚合: {date}" for each day

3. Inject `StatisticsService` into `ScheduleService`.

**Verify:** On first startup with existing visitor_logs, missed aggregation days are backfilled.

## Execution Notes

- **Cron expression conversion:** Go uses 6-field (sec min hour day month dow). NestJS uses 5-field (min hour day month dow). All schedules converted:
  - `0 0 3 * * *` → `0 3 * * *`
  - `0 0 2 * * *` → `0 2 * * *`
  - `0 0 1 * * *` → `0 1 * * *`
  - `0 30 3 * * *` → `30 3 * * *`
  - `0 0 4 * * *` → `0 4 * * *`
  - `0 * * * * *` → `* * * * *`
- **@nestjs/schedule default behavior** prevents concurrent execution of the same cron job (matches Go's `DelayIfStillRunning`)
- **ScheduledBackupJob** will stub BackupService until Plan 10-03 implements it
- **View count Map** is volatile — counts lost on crash. This matches Go backend behavior (Redis cache is also volatile)
