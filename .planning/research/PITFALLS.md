# Pitfalls Research: Go Backend to NestJS + SQLite Migration

**Researched:** 2026-06-28
**Domain:** NestJS + SQLite backend migration with API compatibility
**Confidence:** HIGH

## Summary

This research identifies critical pitfalls when rewriting anheyu-app's Go backend (Gin + Ent ORM + PostgreSQL) to NestJS + Drizzle + SQLite while maintaining API compatibility with the existing Next.js frontend. The primary risks fall into four categories: SQLite limitations, API response format mismatches, concurrency/transaction handling differences, and type system gaps.

**Primary recommendation:** Build an API compatibility test suite in Wave 0 that captures exact Go backend responses, then validate every NestJS endpoint against these golden responses before considering any endpoint complete.

## Critical Pitfalls

### 1. SQLite Concurrency Model Mismatch

**What goes wrong:** Go's PostgreSQL setup handles concurrent writes with row-level locking and transactions. SQLite uses database-level file locks for writes, causing "database is locked" errors under concurrent load.

**Why it happens:**
- PostgreSQL: Multiple concurrent writers with MVCC (Multi-Version Concurrency Control)
- SQLite: Single writer at a time (file-level lock), readers don't block writers but writers block everyone

**Warning signs:**
- `SQLITE_BUSY` errors appearing in logs during file uploads or batch operations
- Upload sessions failing when multiple chunks upload in parallel
- Comment creation failing during article updates

**Prevention strategy:**
- Enable WAL (Write-Ahead Logging) mode: `PRAGMA journal_mode = WAL;`
- Set busy timeout: `PRAGMA busy_timeout = 5000;` (5 seconds)
- Serialize write operations at the application layer using a queue/mutex
- Use connection pooling with `better-sqlite3` or `sql.js` with single connection for writes

**Phase mapping:** Phase 1 (Data Layer Setup) - must address before any write operations

### 2. ID Encoding/Decoding Compatibility

**What goes wrong:** The Go backend uses a custom Sqids encoder with a database-stored seed (`id_seed` setting) to generate public IDs. NestJS must use the identical algorithm and seed, or all frontend references break.

**Why it happens:**
- Go code: `idgen.GeneratePublicID(user.ID, idgen.EntityTypeUser)` uses Sqids with custom alphabet
- Seed stored in database settings table, generated once at first install
- Frontend stores these public IDs in localStorage, URLs, and API calls

**Warning signs:**
- Login fails after migration (user ID decoding returns wrong value)
- Article URLs return 404 (public ID doesn't decode to correct database ID)
- File downloads fail with "invalid ID" errors

**Prevention strategy:**
1. Export the `id_seed` value from Go database before migration
2. Implement identical Sqids encoder in TypeScript (use `sqids` npm package)
3. Create unit tests that verify: `decode(encode(dbId, type)) === dbId` for all entity types
4. Test with real public IDs from the Go backend before switching

**Phase mapping:** Phase 1 (Core Setup) - implement before any API endpoints

---

### 3. JSON Response Format Mismatches

**What goes wrong:** NestJS response structures differ subtly from Go's `response.Success/Fail` format, breaking frontend parsing.

**Why it happens:**
- Go format: `{ "code": 200, "data": {...}, "message": "success" }`
- NestJS default: `{ ...data }` or custom DTOs
- Frontend expects exact structure in API client

**Warning signs:**
- Frontend shows "undefined" for user info after login
- Article lists render empty despite database having data
- Error messages display as "undefined" instead of actual error

**Prevention strategy:**
1. Create a NestJS interceptor that wraps ALL responses in the exact Go format:
   ```typescript
   // response.interceptor.ts
   return {
     code: response.statusCode,
     data: responseData,
     message: responseMessage || 'success'
   };
   ```
2. Capture actual Go responses for key endpoints (login, article list, file upload)
3. Create snapshot tests comparing NestJS output to Go golden responses

**Phase mapping:** Phase 1 (Core Setup) - interceptor must be in place before any controller

---

### 4. JWT Token Format Incompatibility

**What goes wrong:** JWT tokens generated by NestJS don't match Go's token structure, causing frontend auth to fail or tokens to be rejected.

**Why it happens:**
- Go token structure (from code review):
  - Payload includes: `UserID` (public ID string), `UserGroupID` (public ID string), `ExpiresAt`
  - Secret key from settings: `jwt_secret`
  - Algorithm: HS256
- Frontend stores token and sends as `Authorization: Bearer {token}`

**Warning signs:**
- Login succeeds but frontend can't make authenticated requests
- "Invalid token" errors on protected endpoints
- Token refresh fails with decode errors

**Prevention strategy:**
1. Audit Go JWT implementation: check payload structure, secret key source, algorithm
2. Use identical JWT library configuration in NestJS (`@nestjs/jwt` with HS256)
3. Test token round-trip: generate in NestJS, verify frontend can decode and use
4. Keep Go JWT secret in settings table, read same value in NestJS

**Phase mapping:** Phase 1 (Authentication) - before any auth endpoints

---

### 5. File Upload Chunk Handling

**What goes wrong:** Go backend supports resumable chunked uploads with session tracking. NestJS implementation loses state between chunks or generates different session IDs.

**Why it happens:**
- Go code: Session-based upload with UUID session IDs stored in memory/Redis
- Upload flow: `PUT /api/file/upload` → session created → `POST /:sessionId/:index` for each chunk → `POST /finalize`
- Session state includes: file metadata, uploaded chunk indices, temporary file paths

**Warning signs:**
- Large file uploads fail at 50% with "session not found"
- Finalized files are corrupted or incomplete
- Upload progress shows 100% but file never appears in database

**Prevention strategy:**
1. Implement identical session management (use same UUID format)
2. Store session state in SQLite with TTL cleanup (or use Redis if available)
3. Test with files > 100MB to verify chunk handling
4. Verify temporary file paths and cleanup logic

**Phase mapping:** Phase 2 (File Management) - critical for media features

---

### 6. Middleware Execution Order

**What goes wrong:** NestJS middleware/guard/interceptor execution order differs from Go's Gin middleware, causing auth checks to run before request parsing or CORS to fail.

**Why it happens:**
- Gin middleware order: Global → Group → Route-specific
- NestJS: Module-scoped, with complex resolution order
- Critical order: CORS → Body parsing → Auth → Rate limiting → Handler

**Warning signs:**
- OPTIONS preflight requests fail with 401/403
- Request body is undefined in guards
- Rate limiting applies to wrong scope

**Prevention strategy:**
1. Document exact middleware order from Go code:
   - `NoCacheMiddleware()` (anti-cache headers)
   - `middleware.Cors()` (CORS with SiteURL from settings)
   - `SSRProxyMiddleware()` (conditional SSR routing)
   - Route-specific: `JWTAuth()`, `AdminAuth()`
2. Configure NestJS global middleware in exact order
3. Test with browser DevTools Network tab to verify header order

**Phase mapping:** Phase 1 (Core Setup) - before any protected routes

## Common Mistakes

### 1. Assuming SQLite is "Just PostgreSQL Without Features"

**Mistake:** Treating SQLite as a drop-in replacement without adjusting queries or schema design.

**Reality:**
- No native `BOOLEAN` type (use `INTEGER` 0/1)
- No native `DATETIME` (use `TEXT` ISO8601 or `INTEGER` Unix timestamp)
- Limited ALTER TABLE support (can't drop columns, limited modifications)
- Different LIKE behavior (case-sensitive by default)
- No window functions in older SQLite versions

**Prevention:**
- Use Drizzle's schema definitions that map correctly to SQLite types
- Test all queries with actual SQLite, not an in-memory mock
- Verify datetime handling matches Go's time.Time serialization

---

### 2. Not Preserving Redis-Dependent Features

**Mistake:** The Go backend uses Redis for caching (`utility.NewCacheServiceWithFallback`). Removing Redis without replacement breaks rate limiting, session management, and cache-dependent features.

**Reality:**
- Go code shows Redis used for:
  - JWT token blacklisting/refresh
  - Rate limiting counters
  - Image style cache
  - General key-value caching

**Prevention:**
- Keep Redis available OR implement file-based/SQLite caching
- For rate limiting: use SQLite with TTL or in-memory Map with cleanup
- For JWT: ensure token refresh works without Redis (stateless or DB-backed)
- Document which features are degraded without Redis

---

### 3. Ignoring Transaction Isolation Differences

**Mistake:** Assuming SQLite transactions behave like PostgreSQL's SERIALIZABLE isolation.

**Reality:**
- SQLite default isolation: SERIALIZABLE (but implementation differs)
- No row-level locks (table-level or database-level)
- Deadlocks manifest differently (SQLITE_BUSY vs PostgreSQL deadlock errors)

**Prevention:**
- Keep transactions short and focused
- Avoid user input within transactions (minimize lock time)
- Handle SQLITE_BUSY with retry logic

---

### 4. Overlooking Path Handling Differences

**Mistake:** Go's `filepath.Join` works differently on Windows vs Linux. NestJS running on Windows may handle paths differently.

**Reality:**
- Go backend: Windows paths use backslashes
- Node.js: Forward slashes work cross-platform
- File storage paths in database must be consistent

**Prevention:**
- Use Node.js `path.join()` consistently
- Store all paths in database with forward slashes
- Test file operations on target OS

## API Compatibility Risks

### 1. Query Parameter Parsing

**Risk:** Go's `c.Query()` and `c.DefaultQuery()` handle missing parameters differently than NestJS `@Query()`.

**Example from Go code:**
```go
page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))  // defaults to "1" if missing
month, _ := strconv.Atoi(c.Query("month"))            // empty string if missing
```

**NestJS equivalent:**
```typescript
@Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number
@Query('month', new DefaultValuePipe(undefined), ParseIntPipe) month?: number
```

**Verification:** Test all list endpoints with missing/invalid query parameters

---

### 2. Error Message Matching

**Risk:** Frontend may display or check specific error messages from Go backend.

**Example:** Login error messages:
- `"邮箱或密码格式不正确"` (400)
- `"登录失败，请稍后重试"` (500)
- `"两次输入的密码不一致"` (400)

**Prevention:**
- Create error message mapping table
- Use exact Chinese strings in NestJS responses
- Test all error paths

---

### 3. Date/Time Format Consistency

**Risk:** Go's `time.Time` serializes to RFC3339/ISO8601. NestJS/TypeScript Date may serialize differently.

**Go output:** `"2026-01-22T16:15:28Z"` or `"2026-01-22T16:15:28+08:00"`

**NestJS risk:** Without configuration, may output `"2026-01-22T16:15:28.000Z"`

**Prevention:**
- Configure class-transformer or class-validator for consistent serialization
- Test datetime fields in responses (user.created_at, article.published_at)

---

### 4. Null vs Undefined vs Empty String

**Risk:** Go's nil pointers serialize to `null`. TypeScript undefined serializes to missing key. Empty strings may differ.

**Example from Go:**
```go
LastLoginAt *time.Time  // nil → null in JSON
```

**NestJS:**
```typescript
lastLoginAt: Date | null  // null → null
lastLoginAt?: Date        // undefined → key omitted
```

**Prevention:**
- Use `null` consistently for optional fields
- Configure serialization to match Go behavior
- Test with frontend to ensure parsing works

## SQLite Limitations

### 1. Write Concurrency

| Operation | PostgreSQL | SQLite |
|-----------|-----------|--------|
| Concurrent reads | Unlimited | Unlimited |
| Concurrent writes | Unlimited (row-level) | 1 (database-level lock) |
| Read during write | Yes (MVCC) | Yes |
| Write during read | Yes | Blocked |

**Impact on anheyu-app:**
- File uploads (chunked, parallel) may fail
- Comment creation during article updates may timeout
- Batch operations (import/export) block all other writes

**Mitigation:**
- WAL mode + busy timeout (minimum)
- Serialize writes at application layer (recommended)
- Queue system for write-heavy operations

---

### 2. Data Type Limitations

| Type | PostgreSQL | SQLite | Migration |
|------|-----------|--------|-----------|
| BOOLEAN | Native | INTEGER (0/1) | Drizzle handles |
| DATETIME | TIMESTAMPTZ | TEXT/INTEGER | ISO8601 strings |
| JSON/JSONB | Native | TEXT (JSON string) | Serialize/deserialize |
| ARRAY | Native | TEXT (comma-sep) | Custom serialization |
| UUID | Native | TEXT | Store as string |

**Impact:**
- Settings table may store JSON as text
- No native array support for tags/categories
- Datetime comparisons may behave differently

---

### 3. Schema Migration Limitations

**SQLite can't:**
- Drop columns (PRAGMA legacy_alter_table)
- Modify column types (requires table rebuild)
- Add constraints to existing columns (without rebuild)

**Impact:**
- Future schema changes require careful migration planning
- Drizzle migrations must handle SQLite limitations
- May need to recreate tables for major changes

**Mitigation:**
- Use Drizzle's migration tools with SQLite awareness
- Test migrations on copy of production data
- Plan for table rebuild migrations

---

### 4. Full-Text Search Differences

**Risk:** Go backend may use PostgreSQL's `tsvector`/`tsquery` for article search. SQLite FTS5 has different syntax and capabilities.

**Go search service:**
```go
// search.InitializeSearchEngine(settingSvc)
// May use PostgreSQL full-text or plugin-based (Meilisearch)
```

**SQLite FTS5:**
- Different query syntax
- No ranking scores (or different algorithm)
- No stemming by default

**Mitigation:**
- Use SQLite FTS5 with tested query patterns
- Or integrate Meilisearch plugin (already supported in Go code)
- Test search relevance with real queries

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JWT authentication | Custom JWT middleware | `@nestjs/jwt` + `@nestjs/passport` | Standard, well-tested, matches Go patterns |
| Input validation | Manual validation | `class-validator` + `class-transformer` | Declarative, matches Go's binding/validation |
| Response formatting | Manual response building | NestJS interceptors | Centralized, consistent format |
| Database migrations | Custom SQL scripts | Drizzle Kit migrations | Type-safe, rollback support |
| File upload handling | Custom multipart parsing | `@nestjs/platform-express` + Multer | Standard, handles edge cases |
| Rate limiting | Custom counter | `@nestjs/throttler` | Redis/in-memory, configurable |
| Caching | Custom cache logic | `@nestjs/cache-manager` | Redis/memory, TTL support |
| Config management | Manual env parsing | `@nestjs/config` | Validation, defaults, hierarchies |

## Verification Checklist

Before considering any endpoint complete:

- [ ] Response structure matches Go exactly (code, data, message)
- [ ] All field names match (camelCase vs snake_case)
- [ ] Date/time fields serialize identically
- [ ] Null/undefined handling matches
- [ ] Error messages match for all failure paths
- [ ] Query parameter defaults match
- [ ] Authentication flow works with existing frontend tokens
- [ ] Public ID encoding/decoding works for this entity type
- [ ] File uploads work for files > 100MB
- [ ] Concurrent requests don't cause SQLITE_BUSY errors
